# GitHub Actions 自动构建和发布流程

## 第一章：工作流架构设计

### 1.1 工作流文件组织结构

GitHub Actions 工作流文件应存储在仓库的 `.github/workflows/` 目录下。每个工作流对应一个独立的功能模块，采用清晰的命名规范以便于维护。

推荐的工作流文件组织结构：

- `ci-check.yml` - 代码检查工作流
- `ci-test.yml` - 自动化测试工作流
- `build.yml` - 构建打包工作流
- `release.yml` - 版本发布工作流

工作流文件命名应遵循 `功能描述.yml` 的格式，使用小写字母和连字符，确保命名具有描述性和可读性。

### 1.2 工作流依赖关系

各工作流之间存在明确的依赖关系和执行顺序：

1. **代码检查工作流**：在每次代码提交和拉取请求时触发，执行代码质量检查和格式验证。此工作流必须通过后，才能进入后续流程。

2. **自动化测试工作流**：在代码检查通过后自动触发，执行单元测试、集成测试和功能测试。测试覆盖范围包括核心功能模块和边界条件。

3. **构建打包工作流**：在测试通过后，根据触发条件执行构建任务。此工作流会生成 Windows 和 Linux 平台的可执行文件。

4. **版本发布工作流**：仅在创建版本标签时触发，完成最终的构建、打包和发布到 GitHub Releases。

工作流之间通过 `needs` 关键字建立依赖关系，确保前一阶段完成后才能进入下一阶段。同时，通过缓存策略优化重复构建的效率。

## 第二章：代码检查流程

### 2.1 触发条件

代码检查工作流在以下情况下触发：

- **推送触发**：当代码推送到 `main` 分支或 `dev` 分支时自动执行
- **拉取请求触发**：当创建或更新针对 `main` 分支的拉取请求时执行
- **手动触发**：允许通过 GitHub 界面手动触发，用于特殊情况下的检查

触发条件配置应包含路径过滤，仅在相关文件变更时执行检查，避免不必要的资源消耗。

### 2.2 检查项清单

代码检查工作流包含以下检查项：

- **代码格式检查**：验证代码是否符合项目的格式规范
- **语法检查**：检查 Python 代码的语法错误和潜在问题
- **导入检查**：验证模块导入的正确性和循环依赖
- **代码复杂度检查**：确保函数和类的复杂度在合理范围内
- **安全检查**：扫描代码中的潜在安全漏洞
- **文档检查**：验证代码文档的完整性和规范性

每个检查项都有明确的通过标准，任一检查项失败将导致整个工作流失败。

### 2.3 执行步骤

代码检查工作流的执行步骤如下：

1. **环境准备**：配置运行环境，安装必要的依赖和工具
2. **代码检出**：从仓库获取最新代码
3. **缓存设置**：建立依赖缓存以加速后续构建
4. **执行检查**：按照检查项清单依次执行各项检查
5. **结果汇总**：收集所有检查结果并生成报告
6. **通知处理**：根据检查结果通知相关人员

每个步骤都有明确的超时设置，避免工作流长时间挂起。

### 2.4 缓存策略

代码检查工作流采用以下缓存策略：

- **依赖缓存**：缓存 Python 包依赖，避免重复下载安装
- **工具缓存**：缓存代码检查工具，减少工具安装时间
- **缓存键**：基于依赖文件内容生成缓存键，确保依赖变更时更新缓存

缓存配置考虑了跨平台兼容性，为不同操作系统提供独立的缓存空间。

## 第三章：自动化测试流程

### 3.1 触发条件

自动化测试工作流在以下情况下触发：

- **代码检查通过后**：当代码检查工作流成功完成后自动触发
- **推送触发**：代码推送到 `main` 分支或 `dev` 分支时执行
- **拉取请求触发**：针对 `main` 分支的拉取请求更新时执行
- **定时触发**：每日定期执行，确保代码库的持续稳定性

定时触发配置应避开高并发时段，减少对共享资源的影响。

### 3.2 测试类型

自动化测试工作流包含以下测试类型：

- **单元测试**：测试单个函数和类的功能正确性
- **集成测试**：测试模块之间的交互和数据流
- **功能测试**：测试主要功能模块的端到端流程
- **边界测试**：测试极端输入和异常情况的处理
- **回归测试**：验证历史问题的修复和新功能的稳定性

每种测试类型都有对应的测试用例集合，确保覆盖核心功能和关键路径。

### 3.3 测试矩阵配置

测试矩阵配置支持以下测试场景：

- **操作系统矩阵**：Windows 和 Linux 两个主要平台
- **Python 版本矩阵**：支持多个 Python 版本的兼容性测试
- **OCR 引擎矩阵**：测试 PaddleOCR 和 RapidOCR 两种引擎
- **语言环境矩阵**：测试不同语言环境下的运行状态

矩阵配置通过并发执行多个测试任务，提高测试效率和覆盖率。

### 3.4 执行步骤

自动化测试工作流的执行步骤如下：

1. **环境准备**：根据矩阵配置设置测试环境
2. **依赖安装**：安装测试所需的依赖和 OCR 引擎
3. **测试数据准备**：准备测试所需的图片和文档数据
4. **测试执行**：按测试类型依次执行测试用例
5. **覆盖率分析**：收集代码覆盖率数据
6. **结果汇总**：生成测试报告和覆盖率报告
7. **产物归档**：保存测试结果供后续分析

测试执行采用并行策略，同时运行多个测试任务以提高效率。

### 3.5 缓存策略

自动化测试工作流采用以下缓存策略：

- **依赖缓存**：缓存测试依赖和 OCR 引擎文件
- **测试数据缓存**：缓存常用的测试图片和文档
- **覆盖率数据缓存**：缓存覆盖率历史数据用于对比分析
- **增量缓存**：支持基于变更文件的增量测试

缓存策略根据测试文件的变化动态调整，在保证测试准确性的前提下优化执行时间。

### 3.6 失败处理

测试失败时的处理机制：

- **失败通知**：立即通知相关开发人员
- **日志保存**：保存完整的测试日志和错误堆栈
- **截图保存**：保存失败测试的截图和中间状态
- **重试机制**：对偶发性失败提供自动重试功能
- **阻塞策略**：关键测试失败时阻塞代码合并

失败处理配置应平衡严格性和灵活性，避免因非关键问题阻塞开发进度。

## 第四章：构建打包流程

### 4.1 触发条件

构建打包工作流在以下情况下触发：

- **测试通过后**：当自动化测试工作流成功完成后触发
- **版本标签触发**：创建版本标签时执行完整构建
- **手动触发**：通过 GitHub 界面手动触发构建
- **定时触发**：定期执行构建以验证构建环境的稳定性

版本标签触发时将执行完整的构建和打包流程，生成所有平台的发布包。

### 4.2 构建环境

构建打包工作流需要以下构建环境：

- **Windows 环境**：用于构建 Windows 平台的可执行文件
- **Linux 环境**：用于构建 Linux 平台的可执行文件
- **Python 环境**：配置指定版本的 Python 运行环境
- **Qt 环境**：安装 Qt 开发库和相关工具
- **打包工具**：配置 PyStand 和 7-Zip 打包工具

构建环境采用容器化方式，确保环境的一致性和可复现性。

### 4.3 执行步骤

构建打包工作流的执行步骤如下：

1. **环境准备**：配置操作系统和依赖环境
2. **代码检出**：获取指定版本或分支的代码
3. **依赖安装**：安装构建所需的依赖和工具
4. **资源编译**：编译 Qt 资源文件和界面文件
5. **可执行文件生成**：使用 PyStand 生成独立可执行文件
6. **OCR 引擎打包**：打包 PaddleOCR 和 RapidOCR 引擎
7. **多语言资源打包**：打包各语言翻译文件
8. **压缩打包**：使用 7-Zip 创建发布压缩包
9. **自解压包生成**：生成自解压的可执行包
10. **签名验证**：对生成的文件进行完整性验证

构建过程采用增量构建策略，仅重新构建变更的模块，提高构建效率。

### 4.4 缓存策略

构建打包工作流采用以下缓存策略：

- **依赖缓存**：缓存构建依赖和第三方库
- **Qt 缓存**：缓存 Qt 安装文件和编译产物
- **OCR 引擎缓存**：缓存 OCR 引擎文件
- **构建产物缓存**：缓存中间构建产物
- **分层缓存**：按平台和版本分层管理缓存

缓存策略在保证构建正确性的前提下，大幅减少构建时间。

### 4.5 产物命名规范

构建产物的命名遵循以下规范：

- **Windows 压缩包**：`Umi-OCR_Rapid_v{版本号}.7z`
- **Windows 自解压包**：`Umi-OCR_Rapid_v{版本号}.7z.exe`
- **Linux 压缩包**：`Umi-OCR_Rapid_v{版本号}_linux.7z`
- **调试包**：`Umi-OCR_Rapid_v{版本号}_debug.7z`

版本号采用语义化版本规范，格式为 `主版本.次版本.修订号`。产物命名应包含版本号、平台标识和引擎类型，便于用户识别和下载。

## 第五章：版本发布流程

### 5.1 触发条件

版本发布工作流在以下情况下触发：

- **版本标签创建**：创建符合版本规范的标签时触发
- **手动触发**：通过 GitHub 界面手动触发发布流程

版本标签必须遵循 `v{版本号}` 的格式，例如 `v2.1.5`。只有具备发布权限的用户才能触发版本发布流程。

### 5.2 版本规范

版本号遵循语义化版本规范：

- **主版本号**：不兼容的 API 修改
- **次版本号**：向下兼容的功能性新增
- **修订号**：向下兼容的问题修正

发布前需完成以下准备工作：

- 更新版本号信息
- 更新变更日志
- 完成所有测试验证
- 生成发布说明文档

### 5.3 执行步骤

版本发布工作流的执行步骤如下：

1. **标签验证**：验证版本标签格式和权限
2. **代码检出**：获取标签对应的代码版本
3. **完整构建**：执行所有平台的完整构建
4. **产物验证**：验证构建产物的完整性和正确性
5. **签名生成**：生成产物校验和数字签名
6. **Release 创建**：在 GitHub Releases 创建发布页面
7. **产物上传**：上传所有构建产物到 Release
8. **发布说明更新**：更新发布说明和变更日志
9. **通知发送**：发送发布通知给关注者

发布流程采用原子操作，确保要么全部成功，要么全部回滚。

### 5.4 Release 内容模板

Release 页面包含以下内容：

- **标题**：版本号和发布日期
- **发布说明**：版本的主要变更和新功能
- **变更日志**：详细的变更记录，包括新增、修复和优化
- **下载链接**：各平台版本的下载链接
- **校验信息**：文件的校验和和签名信息
- **升级指南**：从旧版本升级的注意事项
- **已知问题**：当前版本的已知问题和限制

Release 内容应清晰完整，便于用户了解版本详情和正确使用。

## 第六章：持续集成策略

### 6.1 触发条件矩阵

持续集成采用矩阵触发策略，支持多种触发场景：

- **分支触发**：`main` 分支、`dev` 分支和功能分支
- **事件类型**：推送、拉取请求、标签创建、手动触发
- **路径过滤**：根据变更文件路径决定是否触发
- **条件过滤**：基于提交信息和标签内容进行过滤

矩阵触发配置确保在合适的时间执行合适的任务，避免资源浪费。

### 6.2 缓存策略

持续集成采用分层缓存策略：

- **依赖层缓存**：缓存 Python 包和系统依赖
- **构建层缓存**：缓存编译产物和中间文件
- **测试层缓存**：缓存测试数据和覆盖率数据
- **工具层缓存**：缓存构建工具和运行时环境

缓存策略采用基于内容的键值对，确保缓存的有效性和一致性。

### 6.3 并发控制

并发控制策略包括：

- **工作流并发**：限制同时运行的工作流数量
- **任务并发**：限制单个工作流内的并发任务数
- **资源竞争**：避免多个工作流同时修改同一资源
- **优先级调度**：根据任务优先级调度执行顺序

并发控制确保资源合理利用，避免竞争和冲突。

### 6.4 失败处理

失败处理机制包括：

- **失败通知**：及时通知相关人员失败信息
- **自动重试**：对偶发性失败提供重试机制
- **失败隔离**：单个任务失败不影响其他任务
- **失败恢复**：提供快速恢复和回滚方案
- **失败分析**：收集失败信息用于问题分析

失败处理应平衡严格性和灵活性，确保系统稳定性的同时不影响开发效率。

### 6.5 安全策略

安全策略包括：

- **权限控制**：严格控制工作流的执行权限
- **密钥管理**：安全存储和管理敏感信息
- **依赖验证**：验证第三方依赖的安全性和完整性
- **代码扫描**：定期扫描代码中的安全漏洞
- **访问日志**：记录所有操作和访问日志

安全策略覆盖工作流的全生命周期，确保系统安全。

### 6.6 性能优化

性能优化措施包括：

- **并行执行**：充分利用并行处理能力
- **增量构建**：仅构建变更的部分
- **缓存优化**：优化缓存策略提高命中率
- **资源限制**：合理分配资源避免浪费
- **监控分析**：持续监控和分析性能瓶颈

性能优化目标是提高构建速度和资源利用率。

## 第七章：监控与维护

### 7.1 监控指标

持续集成需要监控以下指标：

- **构建成功率**：各工作流的成功和失败比例
- **构建时长**：各工作流的平均执行时间
- **缓存命中率**：缓存的使用效率
- **资源使用率**：计算资源的使用情况
- **失败频率**：各类型失败的发生频率
- **恢复时间**：从失败到恢复的平均时间

监控指标应定期收集和分析，用于评估和改进持续集成系统。

### 7.2 定期维护任务

定期维护任务包括：

- **依赖更新**：定期更新依赖到最新稳定版本
- **工具升级**：升级构建工具和运行时环境
- **缓存清理**：清理过期和无效的缓存
- **日志归档**：归档历史日志和报告
- **配置审查**：审查和优化工作流配置
- **文档更新**：更新工作流文档和使用说明

定期维护确保持续集成系统的稳定性和可靠性。

## 第八章：构建环境配置

### 8.1 Docker 容器化构建

#### 8.1.1 容器化优势

采用 Docker 容器化构建具有以下优势：

- **环境一致性**：确保在不同机器上构建环境完全一致
- **版本隔离**：不同版本的依赖和工具相互隔离
- **快速部署**：容器镜像可以快速部署到任何支持 Docker 的环境
- ** reproducibility**：构建过程可重复，确保每次构建结果一致
- **资源效率**：容器共享主机内核，资源占用比虚拟机低

#### 8.1.2 容器镜像设计

容器镜像采用分层设计：

- **基础层**：选择轻量级的 Linux 发行版（如 Alpine Linux）
- **依赖层**：安装 Python、Qt 等基础依赖
- **工具层**：安装构建工具（如 PyStand、7-Zip）
- **应用层**：复制代码和资源文件
- **配置层**：配置环境变量和运行时参数

#### 8.1.3 镜像版本管理

镜像版本管理策略：

- **标签策略**：使用语义化版本标签（如 `v1.0.0`）和 `latest` 标签
- **分层缓存**：利用 Docker 分层缓存特性，只重新构建变更的层
- **镜像仓库**：使用 Docker Hub 或私有仓库存储镜像
- **镜像扫描**：定期扫描镜像中的安全漏洞

#### 8.1.4 容器构建流程

容器构建流程：

1. **基础镜像选择**：选择合适的基础镜像
2. **依赖安装**：安装构建所需的依赖和工具
3. **代码复制**：将代码和资源文件复制到容器中
4. **构建执行**：在容器内执行构建命令
5. **产物提取**：将构建产物从容器中提取到主机
6. **容器清理**：构建完成后清理容器资源

### 8.2 环境标准化

#### 8.2.1 操作系统标准化

- **Windows 环境**：使用 Windows Server 2022 或 Windows 11
- **Linux 环境**：使用 Ubuntu 22.04 LTS 或 CentOS 9
- **Python 版本**：固定使用特定版本的 Python（如 3.10）
- **依赖版本**：所有依赖版本在 `requirements.txt` 中明确指定

#### 8.2.2 工具标准化

- **构建工具**：使用固定版本的 PyStand 和 7-Zip
- **测试工具**：使用固定版本的 pytest 和 coverage
- **代码检查工具**：使用固定版本的 flake8 和 pylint
- **版本控制**：使用 Git 进行版本管理

#### 8.2.3 配置标准化

### 10.4 告警策略

#### 10.4.1 告警级别

告警级别分为：

- **紧急**：构建完全失败，影响产品发布
- **高**：构建成功率显著下降或构建时长大幅增加
- **中**：部分任务失败或性能指标异常
- **低**：轻微的性能下降或警告信息

#### 10.4.2 告警通知方式

告警通知方式：

- **邮件通知**：发送详细的告警信息到相关人员
- **即时消息**：通过 Slack/Teams 发送实时通知
- **SMS 通知**：紧急情况发送短信通知
- **手机应用推送**：通过移动应用发送推送通知

#### 10.4.3 告警处理流程

告警处理流程：

1. **告警接收**：相关人员接收告警通知
2. **问题确认**：确认问题是否真实存在
3. **根因分析**：分析问题的根本原因
4. **解决方案**：制定并实施解决方案
5. **验证修复**：验证修复是否解决了问题
6. **预防措施**：制定预防措施，防止问题再次发生

## 第十一章：故障排查

### 11.1 构建失败分析

#### 11.1.1 失败分类

构建失败主要分为以下几类：

- **依赖失败**：依赖安装失败
- **编译失败**：代码编译或资源编译失败
- **测试失败**：自动化测试失败
- **打包失败**：打包过程失败
- **部署失败**：发布过程失败

#### 11.1.2 失败信息收集

收集以下失败信息：

- **错误日志**：详细的错误堆栈和日志信息
- **环境信息**：构建环境的配置信息
- **依赖信息**：使用的依赖版本
- **代码变更**：相关的代码变更
- **任务状态**：各任务的执行状态

#### 11.1.3 失败定位

失败定位方法：

- **日志分析**：分析构建日志，定位错误位置
- **对比分析**：对比成功和失败的构建
- **逐步调试**：逐步执行构建步骤，定位问题
- **模拟测试**：在本地模拟构建环境进行测试

### 11.2 缓存失效处理

#### 11.2.1 缓存失效原因

缓存失效的常见原因：

- **依赖变更**：项目依赖发生变化
- **工具升级**：构建工具版本升级
- **环境变更**：构建环境配置变更
- **缓存损坏**：缓存文件损坏或不完整
- **策略调整**：缓存策略调整

#### 11.2.2 缓存清理策略

- **自动清理**：根据缓存策略自动清理过期缓存
- **手动清理**：允许手动清理特定的缓存
- **定期清理**：定期清理所有缓存，防止缓存膨胀
- **智能清理**：根据使用频率和有效性清理缓存

#### 11.2.3 缓存恢复

缓存恢复策略：

- **重新构建缓存**：失效的缓存需要重新构建
- **渐进式恢复**：逐步恢复常用的缓存
- **缓存预热**：在高负载前预先填充缓存
- **故障转移**：使用备用缓存源

### 11.3 依赖问题定位

#### 11.3.1 依赖冲突

依赖冲突的定位方法：

- **依赖树分析**：分析完整的依赖树，找到冲突的包
- **版本对比**：对比不同版本的依赖
- **错误信息分析**：根据错误信息定位冲突源
- **逐步排除**：逐步排除可能有冲突的依赖

#### 11.3.2 依赖缺失

依赖缺失的定位方法：

- **依赖检查**：检查项目所需的依赖是否完整
- **源可用性检查**：检查依赖源是否可用
- **网络连接检查**：检查网络连接是否正常
- **权限检查**：检查是否有权限访问依赖源

#### 11.3.3 依赖版本问题

依赖版本问题的定位方法：

- **版本兼容性检查**：检查依赖版本的兼容性
- **API 变更检查**：检查依赖 API 是否有重大变更
- **行为一致性检查**：检查依赖行为是否一致
- **性能影响检查**：检查依赖版本对性能的影响

### 11.4 常见故障案例

#### 11.4.1 Qt 依赖问题

**现象**：构建过程中 Qt 依赖安装失败

**原因**：Qt 安装源不稳定或网络连接问题

**解决方案**：

1. 使用国内镜像源加速下载
2. 增加下载超时时间
3. 预先缓存 Qt 安装文件
4. 检查网络连接稳定性

#### 11.4.2 OCR 引擎下载失败

**现象**：OCR 引擎文件下载失败

**原因**：OCR 引擎下载源不可用

**解决方案**：

1. 配置多个下载源
2. 增加重试机制
3. 预下载并缓存 OCR 引擎
4. 使用本地存储的 OCR 引擎文件

#### 11.4.3 打包工具故障

**现象**：7-Zip 打包过程失败

**原因**：打包工具配置错误或文件权限问题

**解决方案**：

1. 检查打包工具配置
2. 验证文件权限设置
3. 确保有足够的磁盘空间
4. 检查系统资源使用情况
